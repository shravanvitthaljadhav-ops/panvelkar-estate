# V2.0 to Supabase migration map

Status: analysis only; no database migration has been applied.

## Approved baseline
- The approved client reference is Panvelkar Stanford WhatsApp Payment Tool V2.0.
- Preserve the V2.0 interface and behavior. Do not substitute V2.1.
- Keep the public website, existing portal, DNS, RFID, Fancy Dress, and other applications unchanged.
- Free-cost implementation only. Do not create a paid Supabase branch or enable paid services without explicit approval.

## V2.0 source data model (verified from the local V2.0 HTML)
The V2.0 seed contains 428 units: 414 flats and 14 shops. The seed has wing groups R1A, R1B, R2, R3, and R4. This count is a source-file observation, not a live database count.

Existing browser storage keys:
- `stanford_v1_1_data`: unit/member records and transaction arrays
- `stanford_new_comm_template`: legacy/current custom communication template
- `stanford_template_library`: saved template library
- `stanford_active_template_id`: currently active template
- `stanford_last_save`: last browser save timestamp
- `stanford_last_backup`: last manual backup timestamp
- `stanford_daily_backup_YYYY-MM-DD`: daily snapshot containing data, template library, and active template

Unit record fields observed in the V2.0 seed:
`flat`, `name`, `phone`, `phones`, `email`, `otherEmail`, `due`, `received`, `balance`, `payment`, `wa`, `paymentDate`, `flatStatus`, `unitType`, `wing`, `masterUnit`, `waSentAt`, `remarks`.
V2.0 adds/uses a `transactions` array. Each transaction has `id`, `amount`, `date`, and `remarks`.

## Migration mapping (proposed; not yet implemented)
- `payment_units`: one row per unit. Preserve original unit key, member/contact fields, flat status, demand, received, balance, payment status, WhatsApp status, last WhatsApp timestamp, and remarks.
- `payment_transactions`: one row per transaction, linked to its unit. Preserve transaction ID where valid, amount, date, and remarks. Never collapse multiple transactions into a single receipt.
- `payment_templates`: preserve saved template IDs, names, category, message, file name metadata, and active/locked state as applicable.
- `payment_portal_settings`: preserve app-level preferences and active template selection.
- `payment_audit_log`: record actor, action, entity, before/after state, and timestamp for every write.
- `payment_admin_access`: explicit allow-list for individual Admin accounts. Admin count must be configurable (3, 4, or more); never hard-code two accounts.

## Financial integrity rules
1. Transaction history is the source of truth for total received: sum transaction amounts.
2. Outstanding is derived as max(total demand - total received, 0).
3. Payment status is recalculated from demand and received using the V2.0 rules.
4. Editing/deleting a transaction recalculates received, outstanding, payment status, and latest payment date/remarks.
5. Outstanding-only edits follow the approved V2.0 behavior: adjust total demand so that received and transaction history remain unchanged.
6. Upload preview must show matched units and proposed new demand before applying. Updating outstanding must not overwrite names, contacts, flat status, payment history, WhatsApp status, or templates.
7. Migration must be idempotent: rerunning it must not duplicate units, transactions, or templates.

## Security gates
- Supabase Auth individual accounts; no public sign-up.
- Only explicitly allow-listed active Admins can access payment data.
- Member, tenant, and other roles must be denied by default; do not route them to the member dashboard.
- RLS on every payment table. No anonymous policies.
- No service-role/secret key in browser code or repository.
- Admin provisioning must be owner-controlled and separate from ordinary Admin permissions.
- Every write must be attributable to the authenticated Admin and audited.
- Test two or more concurrent Admin sessions and revocation before importing live data.

## Rollout gates
1. Finish schema and policy review; do not apply DDL yet.
2. Build and test the V2.0-compatible integration against synthetic data only.
3. Verify exports, filters, payment calculations, WhatsApp template precedence, and mobile behavior.
4. Verify Admin-only access, RLS, audit trail, session revocation, and no member access.
5. Produce a backup and migration preview; obtain explicit approval before importing any live member data.
6. Configure a genuinely private host only after free-tier privacy and limits are verified.
7. Do not deploy to the live domain or alter DNS until explicitly approved.
